# Roadster Atelier — independent reservation demonstration

Independent Tesla Roadster-inspired design study and working reservation simulation. Not affiliated with Tesla, Inc. No orders, official specifications, prices or payments. Use fictional contact details.

## Local use
Requires Node.js 24 and pnpm 11.19.0. Run `pnpm install --frozen-lockfile`, copy `.env.example` to `.env`, replace the secrets, then run `pnpm start`. Open http://localhost:3000 and /admin.html. Sign in with ADMIN_USERNAME and ADMIN_PASSWORD. npm install and npm start also work; the checked-in lockfile is for pnpm.

## Features
Responsive landing page, fictional configurations, validated submissions, random 96-bit references, public lookup without contact details, admin search/filter/pagination/statistics/status editing, SQLite WAL storage, HttpOnly SameSite=Strict session cookies (Secure in production), CSRF checks, rate limits and security headers. No outgoing email or payment functionality.

## Render
render.yaml defines a paid Starter service and 1 GB persistent disk. Review current costs before creating it.
1. Push this folder to GitHub and connect it as a Render Blueprint.
2. Set ADMIN_PASSWORD to a unique secret of at least 16 characters. SESSION_SECRET is generated by the Blueprint.
3. Verify the disk mount is /var/data and DATABASE_FILE is /var/data/reservations.sqlite.
4. Deploy and visit the HTTPS address. Administrator access is /admin.html, username admin, password configured in Render.
5. Submit a fictional record, change its status, restart and redeploy the service, and verify the same reference survives both operations before declaring hosting persistence verified.

Run one instance only. SQLite requires its mounted disk. TRUST_PROXY=1 assumes one trusted reverse proxy, as configured for Render. Production cookies require HTTPS.

## Persistence and backup
Persistent storage preserves records across normal restarts and deploys; it does not protect against disk deletion, account loss or corruption. Run `node scripts/backup.cjs /var/data/backups/reservations.sqlite` in the service shell for a consistent SQLite backup, then download it to separate storage. Keep backups private. Offsite backup scheduling is not configured. Do not copy only the live SQLite file while WAL writes are active.

To restore: stop the service, preserve the existing database and WAL/SHM files, replace the database with the backup, remove the corresponding old WAL/SHM files, restart and verify records. Never overwrite a live database.

## Verification
Run `pnpm test` for validation, authentication, cookie flags, CSRF enforcement, contact privacy, search, status changes, restart persistence, logout revocation and private path protection. Tests use an isolated temporary database. Run `pnpm audit --prod` for dependency advisories.

## API
GET /api/health
POST /api/reservations
GET /api/reservations/:reference
POST /api/admin/login
POST /api/admin/logout
GET /api/admin/stats
GET /api/admin/reservations (search, status, configuration, page, limit)
PATCH /api/admin/reservations/:reference (status)
DELETE /api/admin/reservations/:reference (administrator removal)

Admin writes require X-Requested-With: RoadsterAdmin and an authenticated session cookie, except login which establishes the session.

This is a demo with one administrator, no MFA/email verification, no automatic retention policy and no scheduled offsite backups. Visitors are explicitly asked to use fictional details. The concept illustration comes from the supplied prototype.
